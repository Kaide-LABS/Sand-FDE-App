# Borno State PHC Worker Reallocation Optimizer

A deterministic, zero-sum staff-reallocation optimizer for Borno State, Nigeria. It reads a
government-published workforce audit, and produces a **specific table of which health-worker
cadres should move from which of Borno's 26 covered LGAs to which, under the constraint that
total headcount never changes** -- not a dashboard, not a hiring plan, a checkable intervention.

This repo is an unsolicited technical artifact accompanying a Forward Deployed Engineer (Nigeria)
application to Sand Technologies. It is Artifact Two of two -- see the [top-level
README](../README.md) for how the two relate. Where [Artifact
One](../artifact-one-data-quality/) proves the ability to tell when data can't be trusted, this
artifact proves the next move: turning a trustworthy, real audit into a defensible, zero-budget
physical intervention, without ever letting a model's judgment stand in for arithmetic a human can
check.

## Quickstart

Requirements: Docker Desktop (or Docker Engine + Compose). No external network calls, no API
keys, no Ministry credentials, no account of any kind -- every input this pipeline reads is a
checked-in CSV under `data/`, extracted once from the PDF in `reference/`.

```bash
git clone <this repo>
cd <cloned-directory>/artifact-two-hr-reallocation

# 1. Start the warehouse (Postgres) and Airflow (standalone mode).
docker compose up -d postgres
docker compose up -d --build airflow

# 2. First boot is slow -- Airflow's standalone mode does a one-time sync of every
#    permission x role combination into its metadata DB. Wait for the webserver to answer:
until curl -s -o /dev/null http://localhost:8081/; do sleep 5; done
# Then get the autogenerated admin password from its logs:
docker compose logs airflow | grep -A1 "Password for user"

# 3. New DAGs start paused in Airflow by default -- unpause it once (from then on it stays
#    unpaused), then trigger a run. Both work from the UI (toggle the pause switch, then
#    click Trigger DAG) or the CLI:
docker compose exec airflow airflow dags unpause borno_hr_reallocation
docker compose exec airflow airflow dags trigger borno_hr_reallocation

# 4. Watch it run (six tasks: load_csv, dbt_seed, dbt_run, dbt_test, optimize,
#    generate_report -- the whole run takes well under a minute, since every input is a
#    small, already-checked-in CSV, not a live pull):
docker compose exec airflow airflow dags list-runs -d borno_hr_reallocation

# 5. Once it finishes, the transfer-proposal report is at:
#    data_snapshots/borno_hr_reallocation_report.html  (open it in a browser)
#    ...and the same data is queryable directly:
docker compose exec postgres psql -U borno -d borno_hr_reallocation \
  -c "select * from dbt_marts.mart_reallocation_input order by lga;"
```

Postgres binds host port `5443` and the Airflow webserver `8081` -- both deliberately distinct
from [`../artifact-one-data-quality`](../artifact-one-data-quality/)'s `5442`/`8080`, so both
artifacts run side by side without a port collision.

If you'd rather not stand up Airflow's web UI at all, every task it orchestrates is also directly
invocable (this is how the pipeline was developed and tested -- Airflow orchestrates the exact
same commands, it does not do anything magic):

```bash
docker compose up -d postgres
docker compose run --rm pipeline python -m ingestion.load_csv
docker compose run --rm pipeline sh -c "cd warehouse/dbt && dbt seed --profiles-dir . && dbt run --profiles-dir . && dbt test --profiles-dir ."
docker compose run --rm pipeline python -m optimizer.main
docker compose run --rm pipeline python -m viz.generate_report
```

To run just the deterministic acceptance suite without Docker at all (it reads straight from
`data/*.csv`, no database needed):

```bash
python -m venv .venv && . .venv/Scripts/activate   # or source .venv/bin/activate on Linux/macOS
pip install -e ".[dev]"
python -m pytest -v
python -m mypy
python -m ruff check . && python -m ruff format --check .
```

## What the pipeline actually does

Borno State's government published a report counting how many health workers -- nurses,
community health officers, and similar roles -- currently work in each of its districts (LGAs),
and roughly how many people live near each district's health facilities. Some districts have far
more workers per person than others.

This pipeline reads that published report (already digitized once, by hand, and independently
re-verified against the raw PDF -- see below) and works out a specific plan for moving some of
those existing workers from over-staffed districts to under-staffed ones, without hiring anyone
new and without changing the total number of workers at all. It only proposes swaps: "move 3
nurses from district A to district B." Every swap can be checked by a person with a calculator:
add up who left each district, add up who arrived, and the two totals must match exactly. The
plan also promises never to strip a district down to zero of any worker type it currently has at
least one of.

1. **Loads** five checked-in CSV extractions of the source PDF's own tables/figures (`data/`) into
   Postgres -- no live pull, no credential, the source is a static government document, not an API.
2. **Runs dbt models** that derive an LGA population proxy (from the PDF's own facility-count and
   facility-density figures, since no population figure exists in the source at LGA grain) and
   join it against current staffing into a single optimizer-ready table.
3. **Solves** a mixed-integer linear program (`scipy.optimize.milp`) that proposes a specific,
   zero-sum set of transfers minimizing the imbalance in staff-to-population ratio across the 26
   LGAs the source data actually covers.
4. **Independently re-verifies** the solver's own output from scratch -- zero-sum, the per-cadre
   floor, and the before/after variance -- using plain arithmetic, never trusting the solver's own
   status report alone.
5. **Renders** a static, self-contained HTML report: the transfer table, the before/after
   variance, and explicit disclosures for the two things this artifact deliberately does not (yet)
   do -- see [Scope boundaries](#scope-boundaries).
6. **Runs on demand** via an Airflow DAG with `schedule=None` -- triggered by a human, not
   continuously scheduled, not hosted anywhere.

## Architecture

```
  reference/borno_phc_baseline.pdf (the source, checked in verbatim)
                |
   (one-time, manual extraction -- see below)
                v
        data/*.csv (5 files, each citing its exact page/table/figure)
                |
                v
        ingestion/load_csv.py
                |
                v
         Postgres (raw schema)
                |
                v
   dbt (staging -> marts) -- warehouse/dbt/models/
   derives the LGA population proxy, joins into
   mart_reallocation_input (26 rows, one per covered LGA)
                |
                v
   optimizer/formulate.py -> optimizer/solve.py (scipy.optimize.milp)
                |
                v
   optimizer/verify.py -- independent recomputation,
   never trusts the solver's own report alone
                |
                v
   viz/generate_report.py -> static HTML report

  Orchestration: airflow/dags/borno_hr_reallocation_dag.py
  (schedule=None, triggered by hand; runs the exact steps above in order)
```

**Ingestion** (`ingestion/`) -- turns the five checked-in CSV extractions into a database.
`config.py` holds file paths, the fixed four-cadre scope for this phase (`PHASE_1_CADRES`), and
the expected totals used to catch a future accidental edit to `data/*.csv`. `models.py` is one
typed record shape per CSV, each rejecting any unexpected column. `load_csv.py` reads the five
files (stripping citation-comment header lines), validates every row, and loads them into
Postgres. `db.py` is the connection helper and the `raw` schema's DDL.

**Warehouse** (`warehouse/dbt/`) -- staging models are a thin pass-through for current staffing
plus the population-proxy derivation (`facility_count / density_per_10k * 10000`); the one mart,
`mart_reallocation_input`, is the single joined table (26 rows) the optimizer actually reads.

**Optimizer** (`optimizer/`) -- the core math. `formulate.py` builds the MILP: which variables
exist (a transfer of one cadre from one LGA to another), what bounds apply (the per-cadre floor),
and the linear objective to minimize. `solve.py` calls `scipy.optimize.milp` and decodes its raw
answer without ever claiming success unless the solver's own status says so. `verify.py`
re-checks the answer from scratch using plain arithmetic -- zero-sum, the floor, and variance --
never trusting `solve.py`'s own report. `main.py` runs the whole chain and writes the result to
Postgres and a dated CSV under `data_snapshots/`.

**Report** (`viz/generate_report.py`) -- reads the latest saved result and writes one
self-contained HTML page: the transfer table, the before/after numbers, the LGA-coverage
disclosure (including the one excluded LGA), the floor-labeling disclosure, and the
not-yet-implemented insecure-ward-flag section.

## The primary source, and what verifying it against the brief found

The research brief that originally proposed this artifact described the source PDF secondhand.
Before any code was written, the actual PDF (`reference/borno_phc_baseline.pdf`) was downloaded
and read in full, and several of its tables were independently re-extracted with `pdfplumber`
(an exact text-layer parser, not a visual read) to eliminate transcription risk. That verification
pass found real, citable discrepancies the brief could not have known about:

- **The staffing gap is 2,860, not 2,628.** The PDF's own Executive Summary states 2,628 -- but
  three other places in the same document (§2.2.1's prose, Table 4, Table 7) all independently
  compute 2,860. This pipeline uses 2,860, the figure the source document's own arithmetic
  actually supports.
- **The source table is missing one of Borno's 27 LGAs entirely.** Table 1 lists exactly 26 LGA
  rows; Guzamala is absent, and the table's own listed rows sum to 3,915 against its own stated
  Grand Total of 3,916 -- a genuine 1-worker inconsistency in the primary source, confirmed via
  independent `pdfplumber` re-extraction, not an artifact of this pipeline's own reading. Guzamala
  cannot be a transfer source or destination in this phase, and its exclusion is disclosed
  explicitly in the rendered report, not silently dropped.
- **No LGA-level or ward-level population figure exists anywhere in the source.** Only a
  state-level total is published. The population figure this pipeline uses is a derived proxy
  from the PDF's own facility-count and facility-density charts, labeled as such everywhere it
  appears -- never presented as if the PDF states it directly.

The full, numbered account of every finding -- eleven of them, each with a page citation -- is in
`ULTIMATE_PRD.md`'s MODERNIZATION CHANGELOG (an internal spec document, gitignored, not part of
this repo -- ask if you'd like a copy). This is the same discipline
[Artifact One](../artifact-one-data-quality/) already established: a number tracing to a real,
cited source is not automatically correct, and this build's own research pipeline produced
exactly this failure mode before, on the same underlying research brief.

## The optimizer's constraints

**Zero-sum, by construction, not by a checked rule.** Every transfer moves headcount from one
named LGA to another; the model has no notion of a worker appearing or disappearing. This is
independently re-verified in `optimizer/verify.py` regardless, since the acceptance criterion
requires a third party be able to check it, not just trust the model's own design.

**The per-cadre floor is this artifact's own invented safety constraint, not a government
standard.** A transfer can never reduce an LGA's headcount for a cadre below 1, if that LGA
currently has 1 or more of that cadre. This prevents the optimizer from proposing something
absurd -- zeroing out a cadre a district currently has -- but it is **explicitly not** a claim
that any LGA meeting this floor meets NPHCDA's actual minimum staffing standard (Table 6: 4
nurses, 6 JCHEWs, 3 CHEWs per facility, for comparison). The report states this distinction
explicitly, in almost the same words as this paragraph, so a reader cannot mistake "floor of 1"
for "meets minimum standard."

**The objective is a linear proxy; the reported variance is computed separately.** True variance
is a quadratic quantity `scipy.optimize.milp` cannot optimize directly. The solver instead
minimizes summed absolute deviation from a fixed target ratio -- a standard linearization. The
actual population variance the acceptance criteria require is computed independently, after the
solve, in `optimizer/verify.py`, using plain arithmetic -- and the report states this distinction
rather than letting a reader assume the solver directly optimized the number being shown.

**A disclosed, non-default optimality gap.** `optimizer/solve.py` accepts any solution within 2%
of the proven optimum (120-second time limit), not an unbounded exact search -- a real problem
found at implementation time (the objective has genuine symmetry across differently-routed but
equally-optimal solutions, making a strict 0%-gap proof take minutes rather than seconds). Every
acceptance criterion (zero-sum, floor, variance strictly improved) holds for any feasible solution
this returns, and the solver status is labeled `optimal_within_2pct_gap`, never a bare `"optimal"`
that would overclaim exact global optimality.

## Why a static HTML report, not Superset

Same reasoning as [Artifact One's own equivalent section](../artifact-one-data-quality/README.md#why-a-static-html-report-not-superset),
independently arrived at rather than copied uncritically: the actual deliverable is one transfer
table plus one before/after comparison -- Superset is a full BI platform built for a different
scale of problem. A static HTML generator gives every stranger who clones this repo the identical
output from one command, with nothing extra to operate or configure, which matters directly for
this artifact's own acceptance criteria (a stranger can verify every number without taking
anything on faith). If anything this argument is stronger here than for Artifact One: this
pipeline has no spatial or interactive-dashboard need at all.

## Why plain Postgres, not PostGIS

Same reasoning as Artifact One, and for the same reason -- nothing in `ingestion/`, `warehouse/dbt/`,
or `optimizer/` contains a single `ST_*` call, geometry column, or boundary join. This pipeline's
LGA "location" is a plain text name, never a coordinate.

## Accountable Autonomy level

**This pipeline operates at Human-in-the-Loop.**

- The optimizer proposes a specific, mathematically optimal (within a disclosed gap) set of
  transfers. It does not execute them, and nothing in this repository connects to a live HR or
  payroll system that could.
- The socio-political and logistical factors that actually determine whether a real transfer is
  viable -- housing at the destination, security risk in conflict-affected LGAs, staff willingness
  to relocate -- are exactly the class of judgment a deterministic optimizer cannot parse, and are
  explicitly excluded from the model rather than scored with an invented weighting.
- **Why this level and not another:** not Supervised Automation, because those excluded factors
  are not merely unweighted -- a human with local knowledge is required to screen every proposed
  transfer before it becomes a real HR action, not just to review an automated decision after the
  fact. Not Human Required, because a wrong or impractical transfer proposal is fully reversible
  (a reviewer rejects it before it changes anything) and low-severity on its own -- this is a
  decision-support draft, explicitly framed as a starting point for the actual authority (the
  SPHCDB HR Director) to review, never a finished recommendation from an outsider.

## Honesty section

**Real (extracted once from a real, checked-in primary source; re-verified independently, not
taken on faith):** all five `data/*.csv` files, `reference/borno_phc_baseline.pdf` itself, and
every domain figure in `ingestion/config.py` used as a drift-detection guard against future edits.

**Synthetic:** none. No staffing figure, population figure, or threshold in this repo is invented
or simulated. The per-cadre floor and the solver's 2% gap tolerance are both explicitly labeled as
this artifact's own engineering choices, never attributed to the source document or to NPHCDA.

**What this artifact deliberately does not attempt (see [Scope
boundaries](#scope-boundaries) for the full, authoritative list):**
- **Facility-level transfers.** The source PDF's Table 1 only reports LGA-level totals, not the
  329-facility breakdown the original research brief assumed existed. Rather than fabricate a
  facility-level split, this pipeline operates entirely at LGA grain -- a coarser, less
  operationally specific proposal, disclosed as a direct consequence of what the primary source
  actually contains.
- **The insecure-ward flag.** The source PDF names 38 insecurity-affected wards but never
  publishes which LGAs they fall in. Rather than proxy this from facility-coverage gaps (a
  measurably different quantity), the report's own insecure-ward panel states plainly that this
  check is not yet implemented, and why -- see the panel itself in the generated report, not a
  silent omission.
- **Two cadres with an unconfirmed name mapping.** "Pharmacist" (the source's staffing table) and
  "Pharmacy Technician" (the source's gap-analysis table) may or may not denote the same role;
  same for "Medical Laboratory Scientist" vs. "Lab Technician." Both pairs are excluded from this
  phase's optimizer rather than guessed at -- the four cadres actually used cover 88% of the
  state's staffing gap regardless.
- **Recruitment, hiring, or any generative AI/LLM component anywhere.** Every number in the output
  comes from deterministic arithmetic or `scipy.optimize.milp`, matching Artifact One's own
  zero-LLM-in-any-correctness-path discipline exactly.

## Acceptance-criteria verification checklist

Every item below is independently checkable by a stranger -- confirmed via a full cold-clone test
(gitignored write-up, not part of the shipped repo -- ask if you'd like a copy), not taken on
faith.

1. **Every proposed transfer traces to a real row in `data/lga_current_staffing.csv`.** Checked by
   `tests/test_zero_sum.py`, `tests/test_floor_constraint.py`, and independently by
   `optimizer/verify.py` at runtime.
2. **The payroll is provably zero-sum** -- exact, not approximate. `tests/test_zero_sum.py`.
3. **No LGA drops below the per-cadre floor.** `tests/test_floor_constraint.py`.
4. **The before/after variance actually improved**, independently recomputed, not read from the
   solver's own self-report. `tests/test_variance_improved.py`.
5. **The rendered report explicitly lists all 26 covered LGAs and names the excluded one
   (Guzamala).** `tests/test_lga_coverage_disclosure.py`.
6. **The floor is explicitly labeled as this artifact's own constraint, distinguished from
   NPHCDA's actual minimum standard.** `tests/test_floor_labeling_disclosure.py`.
7. **The insecure-ward section reads as an honest "not yet implemented" disclosure**, not a
   silent omission or a false-negative "no flags found" -- a posture check, confirmed by direct
   reading, not a string match alone.

## Scope boundaries

Explicitly out of scope for this build: multi-state generalization (Borno-specific throughout);
recruitment or hiring modeling (the source PDF's separate 2,860-worker five-year hiring plan is
untouched -- this pipeline only reallocates the 3,915 who already exist); socio-political or
logistical feasibility scoring inside the optimizer (see [Accountable Autonomy
level](#accountable-autonomy-level)); any live HR or payroll system integration (this is a
one-time, static output from a checked-in extraction, not a continuously running service);
facility-level transfers, the insecure-ward flag, and the two unconfirmed cadre-name mappings
(all three named explicitly in [Honesty section](#honesty-section) above, not silently dropped).
The full, confirmed acceptance criteria and scope edges from this project's own spec-confirmation
process are in `.claude/loopr/baby_prd.md` (local-only, gitignored like Artifact One's own
`.claude/loopr/` -- see that project's README for why); the architecture and every judgment call
made while building it are in `ULTIMATE_PRD.md`, and the file-by-file blueprint this codebase was
built from is in `PHASE_1_SPEC.md` -- both gitignored internal spec documents, same reasoning as
`baby_prd.md`, not part of this repo. A plain-language comprehension pass written after the build
is gitignored too. Ask if you'd like a copy of any of these.

## Repository layout

