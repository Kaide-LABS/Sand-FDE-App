# COMPREHENSION.md — Borno State PHC Worker Reallocation Optimizer

Written for the operator, after Phase 1 (of 1) was implemented, adversarially reviewed, patched,
and approved. Every claim below is grounded in a direct read of the code, tests, and dbt models in
this repository as of commit `cde4d2b` (Phase 1 review approved), plus a live `pytest --cov` run
against the current working tree, not in a restatement of `PHASE_1_SPEC.md` or `ULTIMATE_PRD.md`'s
own prose.

---

## 1. Plain-language walkthrough

Borno State's government published a report counting how many health workers — nurses, community
health officers, and similar roles — currently work in each of its districts (called LGAs), and how
many people live near each district's health facilities. Some districts have far more workers per
person than others.

This project reads that published report (already typed into spreadsheets once, by hand, and
double-checked) and works out a specific plan for moving some of those existing workers from
over-staffed districts to under-staffed ones — without hiring anyone new and without changing the
total number of workers at all. It only proposes swaps: "move 3 nurses from district A to district
B." Every swap it proposes can be checked by a person with a calculator: add up who left each
district, add up who arrived, and the two totals must match exactly. The plan also promises never to
strip a district down to zero of any worker type it currently has at least one of.

The plan is generated by a piece of math (an optimization solver) that tries every reasonable
combination of moves and picks the set that most evens out the worker-to-population balance across
districts. The result is written out as a plain web page: a table of proposed moves, and a
before-and-after comparison of how balanced staffing is. Nothing in this process is guessed or made
up by an AI language model — every number traces back to the government's own published report, or
to a simple, disclosed formula applied to that report's own numbers.

The plan is explicitly a draft for a human decision-maker (a state health workforce director) to
review, not an instruction to be carried out automatically. It also says, in plain terms, two things
it deliberately does not do yet: it does not check whether a proposed move would send workers toward
a district with security problems (because the report doesn't say which districts those are), and it
does not cover one district (Guzamala) at all, because the government's own report has no data for
it — not because that district was checked and found fine.

## 2. Architecture walkthrough

**Ingestion** (`ingestion/`) — turns five checked-in spreadsheet extractions of the PDF into a
database.
- `ingestion/config.py` — file paths, the fixed four-role scope for this phase
  (`PHASE_1_CADRES`), and the expected totals used to catch a future accidental edit.
- `ingestion/models.py` — one typed record shape per spreadsheet, each rejecting any unexpected
  column.
- `ingestion/load_csv.py` — reads the five `data/*.csv` files (stripping citation-comment header
  lines), validates every row, and loads them into Postgres.
- `ingestion/db.py` — the Postgres connection helper and the `raw` schema's table definitions.

**Warehouse / dbt** (`warehouse/dbt/`) — transforms the raw loaded tables into the optimizer's
input.
- `models/staging/stg_lga_current_staffing.sql`, `stg_lga_population_proxy.sql` — thin
  pass-through plus the population-proxy formula (facility count ÷ facility density × 10,000).
- `models/marts/mart_reallocation_input.sql` — the single joined table (one row per district, 26
  rows) the optimizer actually reads.
- `tests/population_proxy_reconciliation.sql`, `tests/mart_reallocation_input_row_count.sql` —
  dbt-level sanity checks.

**Optimizer** (`optimizer/`) — the core math.
- `optimizer/models.py` — the typed shapes for a proposed transfer, a district's before/after
  allocation, and the full result; also `as_cadre()`, a runtime check that a decoded cadre string is
  really one of the four in scope.
- `optimizer/formulate.py` — builds the actual optimization problem: which variables exist, what
  bounds and constraints apply, and the objective to minimize.
- `optimizer/solve.py` — calls `scipy.optimize.milp` and decodes its raw answer, without ever
  claiming success unless the solver's own status says so.
- `optimizer/verify.py` — re-checks the solver's answer from scratch using plain arithmetic
  (zero-sum, the floor, and variance), never trusting `solve.py`'s own report.
- `optimizer/main.py` — runs the whole chain (load → formulate → solve → verify) and writes the
  result to Postgres and a dated CSV file under `data_snapshots/`.

**Report** (`viz/generate_report.py`) — reads the latest saved result from Postgres and writes one
self-contained HTML page: the transfer table, the before/after numbers, the district-coverage
disclosure (including Guzamala's exclusion), the floor-labeling disclosure, and the
not-yet-implemented insecure-ward-flag section.

**Orchestration** (`airflow/dags/borno_hr_reallocation_dag.py`) — a hand-triggered (never
scheduled) chain: load CSVs → dbt seed/run/test → run the optimizer → generate the report.

**Tests** (`tests/`) — `test_csv_sums.py` (spreadsheet totals haven't drifted), `test_zero_sum.py`,
`test_floor_constraint.py`, `test_variance_improved.py` (each independently re-derives an
acceptance criterion from the raw CSVs, without calling `optimizer/verify.py`, so a shared bug
can't hide behind agreement between the two), `test_verify_module.py` (calls the actual shipped
`verify.py` directly — added in the post-review fix), `test_lga_coverage_disclosure.py` and
`test_floor_labeling_disclosure.py` (assert specific sentences appear in the rendered report),
`tests/_test_support.py` (shared CSV-to-input-row helper, not a test file itself).

Every one of these files exists in the repository right now; none is a planned-but-unbuilt
reference.

## 3. Decisions and tradeoffs

- **LGA grain, not facility grain.** The confirmed spec originally assumed facility-level transfers
  ("move 3 CHEWs from Facility A to Facility B"); the source PDF's Table 1 turned out to only report
  district-level (LGA) totals, not per-facility ones. The shipped code (`optimizer/formulate.py`,
  `viz/generate_report.py`) operates entirely at LGA grain. Tradeoff: a coarser, less operationally
  specific proposal, in exchange for never fabricating a facility-level split that doesn't exist in
  the source.

- **Population is a derived proxy, not a fact.** No LGA-level population figure exists anywhere in
  the source PDF. `stg_lga_population_proxy.sql` derives one from two bar charts (facility count,
  facility density) rather than from a real population table. Every place this number is shown
  (`optimizer/models.py`'s `LgaAllocation.population_proxy`, the report's footnote) labels it
  explicitly as derived. Tradeoff: real transcription risk (bar charts have no extractable text
  layer) accepted in exchange for having any population denominator at all, rather than none.

- **Linear objective, quadratic report.** `scipy.optimize.milp` cannot optimize a true variance
  (a quadratic quantity), so `optimizer/formulate.py`'s objective instead minimizes summed absolute
  deviation from a fixed target ratio — a linear proxy. The actual population variance the
  acceptance criteria require is computed separately and independently in `optimizer/verify.py`,
  after the solve, using plain arithmetic. The report (`viz/generate_report.py`) states this
  distinction explicitly rather than letting a reader assume the solver directly optimized the
  number being shown.

- **A disclosed, non-zero optimality gap.** `optimizer/solve.py` sets `MIP_REL_GAP = 0.02` and a
  120-second time limit — not scipy's default of an unbounded exact search. This is not something
  either `PHASE_1_SPEC.md` or `ULTIMATE_PRD.md` mandated; it is an implementation-time engineering
  finding, documented in the module's own docstring: on the actual problem size, proving a strict
  0%-gap optimum was observed to take minutes without converging (the objective only depends on each
  district's net transfer per cadre, not on which specific destination receives it, so many
  differently-routed solutions are equally optimal), while a solution within 2% of optimal was found
  in 10-15 seconds. The status label used (`optimal_within_2pct_gap`, never bare `"optimal"`) makes
  this tradeoff visible rather than silently assumed; every acceptance check still holds for any
  feasible solution returned, not only a proven-exact one.

- **The floor is invented by this artifact, not sourced from NPHCDA.** `_floor_bound()` in
  `optimizer/formulate.py` computes `max(current - 1, 0)` per district per cadre — a constraint the
  builder chose to prevent an absurd proposal (zeroing out a cadre a district currently has), not a
  government minimum-staffing standard. The report's own "per-cadre floor" panel states this
  distinction explicitly, matching the confirmed acceptance criterion's wording almost verbatim.

- **Two acceptance-criterion test files were missing from the spec's own file list, and were built
  anyway.** `tests/test_floor_labeling_disclosure.py` and `tests/test_variance_improved.py` are both
  named by `PHASE_1_SPEC.md` §8's acceptance criteria (criteria 5 and 3) but were omitted from that
  same spec's §1 file list. Both files' own docstrings flag this omission explicitly ("named in
  Sec.8 criterion 5 but omitted from Sec.1's file list; added here to satisfy that acceptance
  criterion") and the code was written anyway — a case of the shipped code correcting a gap in the
  spec's own internal consistency, not deviating from it.

- **The QA pass found and fixed a real 0%-coverage gap in the safety-net module itself.**
  `tests/test_zero_sum.py`, `test_floor_constraint.py`, and `test_variance_improved.py` all
  deliberately re-derive their checks independently rather than calling `optimizer/verify.py` — by
  design, so a shared bug can't hide behind both checks making the same mistake. That discipline had
  a side effect: nothing called the actual shipped `verify_and_build_allocations()` function at all,
  so a bug in `verify.py` itself — the module this project names as its own "never trust the solver
  alone" safety layer — could ship with zero test coverage. Commit `ef41a10` added
  `tests/test_verify_module.py`, which calls the real function directly and cross-checks it against
  an independently-written recomputation, plus a hand-built floor-violation case proving the raise
  path actually fires. Re-running `pytest --cov=optimizer` against the current tree confirms
  `optimizer/verify.py` sits at 98% coverage (the one uncovered line is the zero-sum raise branch,
  which is structurally unreachable given `TransferProposal`'s paired from/to shape).

- **Version pins deliberately trail current-stable.** `docs/modernization_log.md` and
  `ULTIMATE_PRD.md` §7 both name current-stable Airflow (3.3.0) and dbt-core (1.12.2) as of the
  build date, and deliberately pin to the older 2.9.3 / 1.7.x line instead, to match the sibling
  Katsina artifact's own already-proven pins for a two-artifact application read by the same
  reviewers. Disclosed as a consistency choice, not staleness.

## 4. Domain mechanics

Every domain figure below traces to `ULTIMATE_PRD.md` §2's MODERNIZATION CHANGELOG, which is itself
cited to a direct, primary-source read of the Borno State PHC Workers Baseline Mapping Exercise PDF
(Feb 2025) — reused here, not re-derived:

- **3,915 / 3,916 (a 1-worker internal source discrepancy).** `ingestion/config.py`'s
  `EXPECTED_GRAND_TOTAL_SUM = 3_915` encodes Table 1's own listed-row sum, against the same table's
  separately stated Grand Total of 3,916. [Source: `ULTIMATE_PRD.md` §2 finding 9 — pdfplumber
  re-extraction of Table 1.]

- **2,860 (not 2,628) as the state staffing gap.** `ingestion/config.py`'s
  `EXPECTED_GAP_ACROSS_STATE_SUM = 2_860`. The PDF's own Executive Summary states 2,628, but three
  independent places in the same document (§2.2.1's prose, Table 4, Table 7) all compute 2,860; this
  artifact uses 2,860 as the figure the source document's own arithmetic actually supports. [Source:
  `ULTIMATE_PRD.md` §2 finding 1.]

- **26 LGAs, Guzamala absent.** `EXPECTED_LGA_ROW_COUNT = 26` in `ingestion/config.py`, and
  `EXPECTED_LGA_COUNT = 26` in `optimizer/formulate.py`, and `COVERED_LGAS`/`EXCLUDED_LGA` in
  `viz/generate_report.py`. Table 1 lists 26 of Borno's 27 official LGAs; Guzamala has zero
  current-headcount data in the source and cannot be a transfer source or destination in this
  phase. [Source: `ULTIMATE_PRD.md` §2 finding 9, cross-referencing the Nigerian Focus list of
  Borno's 27 LGAs.]

- **329 (facility count).** `EXPECTED_FACILITY_COUNT_SUM = 329` in `ingestion/config.py`. [Source:
  `ULTIMATE_PRD.md` §1/§3.1, Figure 1.]

- **Population proxy formula and its ±5% reconciliation tolerance.**
  `stg_lga_population_proxy.sql` computes `facility_count / density_per_10k * 10000`;
  `population_proxy_reconciliation.sql` checks the summed derived values against the state's own
  facility-count/density identity (329 / 0.8 × 10,000) to within 5%. The dbt test file itself
  discloses the observed reconciliation is ~1.6% (comfortably inside tolerance, and tight enough to
  support a future ±3% tightening not done this phase) and explains explicitly why it is *not*
  reconciled against the state's separately-stated 6.9M population figure (that figure implies a
  ~41% gap against the same identity — a genuine internal inconsistency in the source document,
  not an error in this pipeline's own derivation). [Source: `ULTIMATE_PRD.md` §3.2, §2 finding 3.]

- **The four in-scope cadres cover 88% of the state's gap.** `PHASE_1_CADRES` in
  `ingestion/config.py` (Community Health Officer, Community Health Extension Worker, Junior CHEW,
  Nurse/Midwife) are the four cadres with an exact name match between Table 1 and Table 4/6/7;
  together they account for 974+216+188+1,138 = 2,516 of the state's 2,860-worker gap. [Source:
  `ULTIMATE_PRD.md` §5.]

- **The per-cadre floor (`max(current − 1, 0)`) is not a domain figure at all** — it is this
  artifact's own invented safety constraint, explicitly distinguished in the rendered report from
  NPHCDA's actual minimum-standard table (Table 6, PDF p.26). No citation applies because none is
  claimed; the report's own "per-cadre floor" panel states this distinction in those words.

- **The 2% MIP relative-gap tolerance and 120-second solver time limit** (`optimizer/solve.py`) are
  an engineering parameter, not a domain figure — self-measured by the builder against this
  project's own actual problem size (documented in the module docstring: "proving a strict 0%-gap
  global optimum was observed to take minutes... a solution proven within 2%... found in ~10-15s"),
  not sourced from any external reference. Marked here explicitly as [ENGINEERING, SELF-MEASURED],
  distinct from the PDF-sourced domain figures above.

No domain figure encoded in this phase's code was found stated without a traceable source or an
explicit marker.

## 5. Honesty audit

Compared every `PHASE_1_SPEC.md` clause against the code actually read this run, with particular
attention to the insecure-ward-flag disclosure (§6 step 8, §9), the single highest-consequence
failure mode `ULTIMATE_PRD.md` §11 names.

**Insecure-ward disclosure: confirmed correct, no gap.** Read `viz/generate_report.py` lines
344–364 directly. The rendered HTML includes a panel titled "Insecure-ward flag — not yet
implemented," with a `class="panel unimplemented"` / `class="warn"` styled block stating plainly
that the flag "is not yet implemented, not silently omitted and not a false-negative 'no flags
found'," naming the 38-ward figure and the missing per-LGA breakdown, and explicitly stating why the
project does not proxy this from facility-coverage gaps. This is a genuinely rendered, non-empty,
correctly-worded disclosure — not a silent omission and not a false "no flags" placeholder. This
matches `PHASE_1_SPEC.md` §6 step 8 and §7's guard exactly.

**Real, concrete gap found: automated test coverage does not reach the database-writing and
database-reading code paths.** Running `pytest --cov=optimizer --cov=ingestion --cov=viz` against
the current tree (not assumed from the commit message) shows `optimizer/main.py` at **0%** coverage
and `viz/generate_report.py` at **74%**, with the uncovered lines being exactly
`fetch_latest_run()` (the Postgres read) and `main()` (the Postgres-driven report-write entry
point). This is disclosed — commit `ef41a10`'s own message states "`optimizer/main.py`'s DB-write
orchestration remains untested by the automated suite... manually verified instead via two full
docker-compose runs" — but it is still a real, present gap between the project's own stated
discipline ("never trust one layer's self-report alone," `ULTIMATE_PRD.md` §11) applied everywhere
else in this codebase, and the two modules that actually touch a live database, which rely on manual
verification rather than an automated test. Any future change to `optimizer/main.py` or
`fetch_latest_run()` would not be caught by the automated suite.

**Minor, non-functional gap: a naming mismatch between the PRD and the shipped file.**
`ULTIMATE_PRD.md` §3.1 names the CSV-sum safeguard test `tests/test_pdf_extraction_sums.py`; the
file actually built (matching `PHASE_1_SPEC.md`'s own, later, file list) is `tests/test_csv_sums.py`.
Content and behavior match what both documents describe; only the filename differs between the two
planning documents themselves, not between either document and the code.

## 6. Open items

- **Insecure-ward-to-LGA mapping (`ULTIMATE_PRD.md` §8 item 1).** Still unresolved. Phase 1's own
  code deliberately does not implement this — `PHASE_1_SPEC.md` §9 names it as an explicit
  non-goal — and instead ships the disclosure panel verified in §5 above. Resolving it requires
  either a supplementary section of the underlying State HRH database or direct confirmation from
  Borno SPHCDB; neither has happened as of this pass.

- **Pharmacist / Lab cadre-name ambiguity (`ULTIMATE_PRD.md` §8 item 2).** Still unresolved.
  `PHASE_1_CADRES` in `ingestion/config.py` remains fixed at four cadres; Pharmacist and Medical
  Laboratory Scientist are not decision-variable cadres anywhere in the shipped code. Not blocking —
  the four in-scope cadres already cover 88% of the state's gap — but genuinely open for a future
  phase, not resolved by anything built here.

- **`optimizer/main.py` and `viz/generate_report.py`'s database-touching paths lack automated test
  coverage** (§5 above). Currently mitigated only by manual `docker-compose` verification, which is
  not repeatable by an automated CI run and was not re-run as part of this comprehension pass (this
  pass is documentation-only and made no code or infrastructure changes). A future phase touching
  either module should either add a live-Postgres test fixture or re-run the same manual check.

- **dbt population-proxy reconciliation tolerance left at ±5% despite an observed ~1.6% gap.**
  `PHASE_1_SPEC.md` §6 step 2 itself anticipates tightening "once real reconciliation is observed";
  the test file's own comment states the observed 1.6% would support tightening to ±3%, but this was
  deliberately not done this phase since Phase 1 is a one-time run rather than a recurring pipeline.
  Flagged here as a reasonable, still-open future tightening, not a defect.
