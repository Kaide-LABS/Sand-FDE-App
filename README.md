# Katsina State LGA Data-Toxicity Audit

A deterministic data-quality triangulation pipeline for Katsina State, Nigeria.
It ingests genuinely open Nigerian health data (MSDAT aggregate indicators,
GRID3 population baselines), runs two deterministic checks over it, and
produces a **ranked list of which of Katsina's 34 LGAs have the least
trustworthy reported data, and why** -- not a health-metrics dashboard.

This repo is an unsolicited technical artifact accompanying a Forward
Deployed Engineer (Nigeria) application to Sand Technologies. Sand's own
public position is "Foundations Over Features": that generative AI and
dashboards built on top of broken data are the wrong first move, and that the
unglamorous work of finding out *where the data itself can't be trusted* is
the right one. This repo tries to demonstrate that kind of work directly, in
Sand's own stack, rather than describe it.

## Quickstart

Requirements: Docker Desktop (or Docker Engine + Compose), and an internet
connection (the pipeline pulls live from MSDAT and GRID3/WorldPop). No
Ministry credentials, no account of any kind, no API keys.

```bash
git clone <this repo>
cd Sand_FDE

# 1. Start the warehouse (Postgres + PostGIS) and Airflow (standalone mode).
docker compose up -d postgres
docker compose up -d --build airflow

# 2. First boot is slow -- Airflow's standalone mode does a one-time sync of
#    every permission x role combination into its metadata DB, which took
#    several minutes in testing (SQLite, no tuning). Wait for the webserver
#    to answer:
until curl -s -o /dev/null http://localhost:8080/; do sleep 5; done
# Then get the autogenerated admin password from its logs:
docker compose logs airflow | grep -A1 "Password for user"

# 3. New DAGs start paused in Airflow by default -- unpause it once (from
#    then on it stays unpaused), then trigger a run. Both work from the UI
#    (toggle the pause switch, then click Trigger DAG) or the CLI:
docker compose exec airflow airflow dags unpause katsina_data_toxicity_audit
docker compose exec airflow airflow dags trigger katsina_data_toxicity_audit

# 4. Watch it run (five tasks: fetch_msdat, fetch_grid3, dbt_seed, dbt_run,
#    dbt_test, generate_report -- fetch_msdat takes the longest, ~2-3
#    minutes, since it makes ~800 paced HTTP calls against MSDAT's public API
#    politely rather than hammering it).
docker compose exec airflow airflow dags list-runs -d katsina_data_toxicity_audit

# 5. Once it finishes, the ranked audit list is at:
#    data_snapshots/toxicity_audit_report.html  (open it in a browser)
#    ...and the same data is queryable directly:
docker compose exec postgres psql -U katsina -d katsina_data_quality \
  -c "select lga_name, toxicity_score, toxicity_reasons from dbt_marts.lga_data_toxicity_audit order by toxicity_score desc limit 10;"
```

If you'd rather not stand up Airflow's web UI at all, every task Airflow runs
is also directly invocable (this is how the pipeline was developed and
tested -- Airflow orchestrates the exact same commands, it does not do
anything magic):

```bash
docker compose up -d postgres
docker compose run --rm pipeline python -m ingestion.fetch_msdat
docker compose run --rm pipeline python -m ingestion.fetch_grid3
docker compose run --rm pipeline sh -c "cd warehouse/dbt && dbt seed --profiles-dir . && dbt run --profiles-dir . && dbt test --profiles-dir ."
docker compose run --rm pipeline python -m viz.generate_report
```

## What the pipeline actually does

1. **Ingests** MSDAT's NHMIS (Facility-based) coverage indicators for all 34
   Katsina LGAs (live pull against MSDAT's real API -- see below) and GRID3's
   LGA-level population estimates for the same 34 LGAs (live pull against the
   official WorldPop mirror).
2. **Runs dbt models and dbt tests** implementing two deterministic
   constraints (below).
3. **Outputs** a ranked LGA data-toxicity audit list: for every LGA, a
   `toxicity_score` and a human-readable `toxicity_reasons` string, ordered
   worst-first. This is the deliverable. It does not compute, display, or
   rank any health outcome -- only the reliability of the reporting itself.
4. **Renders** that list as a static HTML report (see
   [below](#why-a-static-html-report-not-superset) for why not Superset).
5. **Runs on demand** via an Airflow DAG with `schedule=None` -- triggered by
   a human, not continuously scheduled, not hosted anywhere.

## The MSDAT investigation

The spec's one open technical question going into the build: does MSDAT
(https://msdat.fmohconnect.gov.ng/) expose a scrapable API or structured
export? `VERIFIED_SOURCES.md` recorded this as unresolved before the build
started -- a plain HTTP fetch of the page returns only a Vue.js single-page-app
shell, no data. Resolving it honestly, before writing any ingestion code
around an assumption, was the first task.

**What was actually done**, in order:

1. Fetched the raw HTML of `https://msdat.fmohconnect.gov.ng/` and
   `https://msdat.old.fmohconnect.gov.ng/` directly. Both are Vue.js SPA
   shells (`<div id="app"></div>` plus bundled JS) -- confirms the page
   itself carries no data, as `VERIFIED_SOURCES.md` already suspected, but
   nothing more.
2. Downloaded and searched the site's own shipped JS bundles
   (`js/app.<hash>.js`, `js/chunk-vendors.<hash>.js`, ~5MB combined) for
   hardcoded API base URLs. Found a real backend:
   `https://msdat-api.fmohconnect.gov.ng/api/`.
3. Probed that API directly with plain HTTP requests. Its metadata endpoints
   (`/api/subsections/`, etc.) were open, but the endpoints that actually
   carry indicator values (`/api/data/`, `/api/indicators/`) returned
   `401 Missing or invalid token header format`.
4. Rather than guess at the auth scheme, launched a real headless browser
   (Playwright + Chromium) against the live dashboard and inspected the
   actual network requests it made -- i.e. the "browser network-tab
   inspection" `VERIFIED_SOURCES.md` had flagged as the next step. This
   surfaced a `POST {api}auth/frontend-token/` call, authenticated with two
   header values (`x-frontend-key-id`, `x-frontend-auth`), that returns a
   short-lived (~15 minute) JWT used for every subsequent data call.
5. Searched the JS bundle again, specifically for where those two header
   values come from. They are **static, shipped in plaintext** inside the
   bundle itself, as build-time environment variables
   (`VUE_APP_FRONTEND_KEY_ID`, `VUE_APP_FRONTEND_AUTH`). This is not a
   dynamically-computed, per-session secret -- it is a fixed value baked into
   MSDAT's own publicly-served JavaScript.
6. Confirmed the browser was not actually load-bearing: replicated the exact
   same `POST` with plain `requests` (no browser, no JS execution) and got
   back a working token, which then successfully authorized `GET
   /api/data/...` calls returning real indicator values. `ingestion/msdat_client.py`
   is exactly this -- roughly 100 lines of `requests` code, no headless
   browser dependency at runtime.

**A deliberate implementation choice that follows from this:** the two header
values are genuinely public (shipped in plaintext to every browser that loads
the page), but this repo does not pin them as literal constants anywhere in
its source. `ingestion/msdat_key_discovery.py` re-extracts them at the start
of every pipeline run, the same way described in steps 2 and 5 above --
fetch the homepage, find the current JS bundle URL, regex the two values out
of it. This is not caution theater: a value hardcoded today would silently
go stale the moment MSDAT redeploys with a new bundle hash or rotates the
value, and a credential-shaped literal sitting in a public repo's source
(regardless of how public the underlying value actually is) is exactly the
kind of thing that reads badly to both automated secret scanners and a human
reviewer's first `git log -p` -- an unnecessary own-goal for an artifact
whose whole point is demonstrating engineering judgment. Extracting it at run
time costs one extra HTTP round trip per pipeline invocation and avoids both
problems.

**Conclusion:** MSDAT does expose a real, scrapable, structured API, and it
requires zero Ministry credentials -- the "authentication" is the same static
key every anonymous browser that loads the public dashboard already uses,
extracted at run time from MSDAT's own public JS, never hardcoded in this
repo. This is meaningfully different from "no API" (the state
`VERIFIED_SOURCES.md` left this in) and also different from "here is a
Ministry API key" (which would have been out of scope) -- it is closer to
"the public website's own client secret, which by construction every
visitor's browser already has, extracted the same way a browser gets it
rather than copy-pasted." The spec's fallback path (manual
extraction from the visible dashboard, checked in as a labeled CSV) was
**not needed** -- it's documented here as the honest record of what was tried
before concluding it wasn't necessary, not as the chosen path.

**A real resolution limit found along the way, not glossed over:** MSDAT's
`NHMIS (Facility-based)` datasource (id 6) publishes LGA-level values, but
only at **annual** grain. A second datasource, `NHMIS monthly
(Facility-based)` (id 30), does publish true month-grain periods -- but only
at **State and National** level; querying it for any Katsina LGA location ID
returns zero rows, confirmed by direct query, not assumed. True LGA-by-month
data exists only inside raw facility-level DHIS2/NHMIS, which is explicitly
out of scope (credential-gated, per the boundary this build was locked to).
This is why the reporting-volume-attrition constraint operates **year-over-year**
rather than month-over-month -- see
[The two deterministic constraints](#the-two-deterministic-constraints)
and the full rationale in
`warehouse/dbt/models/marts/lga_reporting_attrition.sql`.

The complete evidence trail -- every endpoint probed, every response --
is recorded in `VERIFIED_SOURCES.md` under "Resolved during the build phase."

are in `VERIFIED_SOURCES.md` -- this section summarizes what each source is
used for.

| Source | What it provides | Used for |
|---|---|---|
| [MSDAT](https://msdat.fmohconnect.gov.ng/) (Federal Ministry of Health, Nigeria) | LGA-level, annual NHMIS coverage-indicator values, 2015-2025, for all 34 Katsina LGAs | The `value` this pipeline checks for attrition and impossibility |
| [GRID3/WorldPop bottom-up gridded population estimates for Nigeria, v1.2](https://data.humdata.org/dataset/bottom-up-gridded-population-estimates-for-nigeria) (CC BY 4.0) | LGA-level population point estimates + 95% uncertainty interval, for all 34 Katsina LGAs | The independent population denominator for the biological-impossibility test |

## The two deterministic constraints

Both are implemented as dbt models (the computation) plus dbt tests
(`warehouse/dbt/tests/*.sql`, `severity=warn` -- a "failing" test here means
*toxic LGAs were found*, which is this pipeline doing its job, not a defect;
`severity=warn` means `dbt test` surfaces and counts every violation without
treating it as a build-breaking error).

### 1. Reporting-volume attrition

**Model:** `warehouse/dbt/models/marts/lga_reporting_attrition.sql`

For each LGA, out of a basket of 24 MSDAT indicators that are tagged
LGA-level + (facility-)monthly-reported in MSDAT's own metadata, how many
actually have a reported value in a given year ("completeness_fraction"),
compared year-over-year.

**Why year-over-year, not month-over-month:** see
[The MSDAT investigation](#the-msdat-investigation) -- MSDAT's public
LGA-level aggregate simply does not publish at month grain; only raw
facility-level DHIS2 does, and that's out of scope. The test operates at the
actual resolution the open data supports rather than fabricate a monthly
signal from data that isn't there.

**Threshold, grounded in the Gombe State study** (Bhattacharya et al. 2019 --
Katsina's own completeness has not been separately measured; these numbers
justify the *order of magnitude* of a non-arbitrary threshold, they are not
claimed as Katsina's own figures):

- Flag if `completeness_fraction < 0.33` -- the same order of magnitude as
  Gombe's own worst-performing indicators (anemia/proteinuria screening,
  malaria IPT), which fell under 25-33% of expected reports.
- Flag if the year-over-year relative drop is `>= 0.50` -- the same order of
  magnitude as Gombe's documented under-reporting rate (referral facilities
  under-reported skilled-birth-attendant deliveries by more than 50%).

**A finding worth being explicit about:** in a live run against Katsina's
real data, most LGAs show completeness dropping by roughly 30-40% in the
final year of the series (2025) relative to the year before -- but this
happens almost everywhere, uniformly, not just in a toxic subset of LGAs. It
is consistent with MSDAT's own disclosed ~2-month reporting lag (the most
recent year in any live-pulled dataset will always look artificially
incomplete relative to fully-settled prior years). Because the thresholds
above are calibrated to Gombe's actual severity magnitudes rather than any
year-over-year change at all, this test correctly does **not** fire on that
uniform, expected, already-disclosed platform characteristic -- it exists to
catch an LGA-specific collapse in reporting, not the ordinary tail of a
still-settling year. This is a deliberate design property, not a gap: a
threshold that flagged every LGA for the disclosed lag would be noise, not
signal.

### 2. Biological impossibility

**Model:** `warehouse/dbt/models/intermediate/int_lga_impossibility_detail.sql`,
aggregated in `warehouse/dbt/models/marts/lga_biological_impossibility.sql`

Restricted to the subset of MSDAT indicators (12 of the 24) for which MSDAT's
own metadata documents an explicit, fixed population-fraction denominator in
plain text -- e.g. ANC Coverage (1 Visit): *"5% of the total population"*;
DPT3/Penta 3 coverage: *"4% of the total population"*. These strings are
quoted directly from MSDAT's own API response (`ingestion/config.py` and
`warehouse/dbt/seeds/indicator_reference.csv` both carry them verbatim), not
inferred or invented.

For each such indicator/LGA/year: the eligible population is recomputed as
`GRID3_population_estimate x population_fraction` -- **using GRID3's
population figure, not MSDAT's own (undocumented) one** -- so the check is an
external, independent test, not MSDAT re-checking its own arithmetic. A row
is flagged `is_impossible` when MSDAT's reported coverage percentage, applied
to that GRID3-derived eligible population, implies more people were served
than the target group could physically contain (`value > 100%`). A stronger
`is_extreme_impossible` flag fires when the implied headcount would exceed
GRID3's **entire** LGA population, not just the documented target
sub-group -- i.e. even the most generous possible misreading of the
denominator still can't explain the number.

In a live run, this test found genuinely striking real findings -- e.g. one
LGA's series includes a reported coverage value of several thousand percent
for a single indicator in a single year. That is not a synthetic example
constructed to make the pipeline look good; it is what MSDAT's own live data
contains, and finding it deterministically -- without any LLM or subjective
judgment -- is exactly what this constraint is for.

### The final ranked list

`warehouse/dbt/models/marts/lga_data_toxicity_audit.sql` joins both
constraints per LGA into a single `toxicity_score`:

```
toxicity_score =  3  x reporting_attrition_flag
                +  1  x impossible_incident_count
                +  2  x extreme_impossible_incident_count
```

This is a transparent triage weighting, not a certified statistical index --
its job is to tell a human data steward where to look first, with the full
`toxicity_reasons` text and every underlying number available right beside
it, not to stand in for their judgment.

## Why a static HTML report, not Superset

The stack constraints name Superset **or** "an equivalent lightweight local
visualization if standing up Superset is disproportionately heavy for this
scope." This build chose the lightweight equivalent
(`viz/generate_report.py`), because:

- The actual deliverable is one ranked table plus one bar chart -- Superset
  is a full BI platform (its own metadata database, an admin-user bootstrap
  step, and chart/dashboard authoring through its UI or a scripted
  equivalent) built for a very different scale of problem.
- A static HTML generator gives every stranger who clones this repo the
  *identical* output from one command, with no extra service to operate and
  nothing to click through to configure -- which matters directly for
  acceptance criterion 1 (a stranger can verify this end-to-end without
  taking anything on faith).
- Standing up Superset well (auth, a real chart, a real dashboard) would have
  added real operational surface area for a payoff this small. That trade-off
  itself is a "Foundations Over Features" call: build the thing that's
  actually needed, not the impressive-looking thing.

The report is written to `data_snapshots/toxicity_audit_report.html` and is a
single self-contained file (inline CSS, no external requests, no JS
framework) -- open it directly in a browser.

## Accountable Autonomy level

**This pipeline operates at Supervised Automation.**

- The two constraints run **automatically** and deterministically -- no
  human approves each individual flag before it's computed; `dbt test`
  executes both checks every run and every violation is surfaced.
- But the pipeline's own authority stops at **flagging**. Nothing is
  auto-corrected, no record is deleted, no funding or programmatic decision
  is triggered by a flag. A human data steward reviews the ranked list and
  the full `toxicity_reasons` for each flagged LGA, and retains an override
  window before anything downstream happens.
- **Why this level and not another, tied to consequence severity and
  reversibility:**
  - Not **Full Automation**: a flag here could plausibly feed into a
    consequential downstream decision (e.g. where a state office chooses to
    investigate reporting practices, or how it weighs an LGA's figures in
    planning) that this artifact deliberately does not make itself. Full
    Automation would mean the flag *is* the decision; it isn't.
  - Not **Human-in-the-Loop** (requiring a human to approve each flag
    *before* it's even computed): that would defeat the actual value of using
    dbt as a repeatable, deterministic gate -- the entire point of automating
    the unglamorous detection work is that it runs the same way every time,
    consistently, on demand. Gating computation itself behind per-flag human
    approval would just reintroduce the manual-audit bottleneck this pipeline
    exists to remove.
  - Not **Human Required** (no automation at all): that level is for
    catastrophic, hard-to-reverse consequences -- e.g. an automated clinical
    or treatment decision. A false-positive data-quality flag is fully
    reversible (a steward reviews it, finds it unwarranted, and moves on) and
    low-severity on its own (it flags *reporting reliability*, it does not
    touch patient care, and it makes no claim about why the data is bad or
    what to do about it).
  - **Supervised Automation** is the level where the automation is trusted to
    run and to flag, but a human is structurally required before any
    consequential action follows, and the worst case of a wrong flag is
    cheap and reversible. That is what this pipeline actually does.

## Honesty section

**Real (live-pulled, re-executed every run):**
- MSDAT NHMIS (Facility-based) LGA-annual coverage-indicator values for all
  34 Katsina LGAs, 2015-2025 -- pulled from MSDAT's real API on every
  pipeline run (`ingestion/fetch_msdat.py`).
- GRID3/WorldPop LGA-level population estimates for all 34 Katsina LGAs --
  downloaded from the official WorldPop mirror on first run and cached
  locally thereafter, since it is a static dataset release, not a live feed
  (`ingestion/fetch_grid3.py`).

**Synthetic:** none. No indicator value, population figure, or threshold in
this repo is invented or simulated.

**Manually-extracted / semi-mocked:** none. The spec anticipated MSDAT might
force a manual-extraction fallback (reading values off the visible dashboard
and checking them in as a labeled CSV) if no scrapable API could be found.
Investigation found a genuine, working, credential-free API instead (see
[The MSDAT investigation](#the-msdat-investigation)), so that fallback was
never triggered. This is stated explicitly, not silently -- the fallback path
was a real possibility going in, not a hypothetical this README raises for
completeness.

**What this artifact deliberately does not attempt:**
- **National scale.** Bounded to Katsina State's 34 LGAs, on the strength of
  its AFENET/Yamma-2 precedent (see the locked scope in `.claude/loopr/baby_prd.md`
  if you have access to it; the boundary itself is restated here for anyone
  who doesn't).
- **Ward-level analysis.** GRID3 does publish ward-level population, but
  MSDAT does not publish indicator data below LGA level in its public
  aggregate -- disaggregating to ward would require inventing a distribution
  this pipeline has no basis for, so the audit stays at LGA grain throughout,
  matching the deliverable's own required output shape.
- **Diagnosing *why* a given LGA's data is bad**, or recommending what to do
  about it. The pipeline flags; it does not explain root cause or prescribe
  action -- that is explicitly a human data steward's job, per the
  Accountable Autonomy level above.
- **Any generative AI / LLM / RAG component**, anywhere, including as a
  "just summarize the findings" convenience. Every flag, every threshold, and
  every number in the ranked list comes from deterministic SQL over live
  data.
- **Clinical prediction** of any kind (e.g. forecasting disease burden or
  outcomes).
- **Cold-chain / stock-out simulation.** The one real, correctly-scoped
  stock-out figure available (Bauchi State, pre-intervention, ~39% -- see
  `VERIFIED_SOURCES.md`) is a different state and a different data-generating
  process than Katsina's reporting data; simulating consequences on top of it
  would not be traceable to a primary source for Katsina and was explicitly
  out of scope from the start.
- **Geospatial clinic-siting or "dark settlement" discovery** (Sand's own
  Rwanda methodology, and AFENET/GRID3's already-published Nigeria work --
  out of scope as anti-replication of both).
- **Ingesting any credential-gated source**: raw DHIS2/NHMIS facility-level
  data, NDHS/DHS microdata, EMID/NPHCDA backend, NSHIP raw data. Only MSDAT's
  public aggregate and GRID3 are ingested.
- **Any hosted or continuously-running deployment.** The Airflow DAG has
  `schedule=None`; nothing in this repo runs unattended or is deployed
  anywhere beyond the reader's own machine.

## Acceptance-criteria verification checklist

Every item below is independently checkable by a stranger -- not taken on
faith.

1. **`git clone` + README, zero Ministry credentials, runs end-to-end
   against live pulls.** Follow [Quickstart](#quickstart). `ingestion/fetch_msdat.py`
   and `ingestion/fetch_grid3.py` make real outbound HTTPS calls on every
   invocation (watch `docker compose logs` -- there is no code path that
   reads a checked-in "real" dataset instead of calling out). No credential,
   API key, `.env` secret, or login of any kind is required anywhere in this
   repo.
2. **Output is a ranked LGA data-toxicity list, not a health-metrics
   dashboard.** `dbt_marts.lga_data_toxicity_audit` and
   `data_snapshots/toxicity_audit_report.html` both show `toxicity_score` /
   `toxicity_reasons` per LGA, ranked worst-first. No health outcome
   (mortality, coverage-as-a-target, etc.) is displayed or ranked anywhere in
   the output -- only the reliability of the reporting itself.
3. **Every factual claim resolves to a cited primary source in the repo.**
   `VERIFIED_SOURCES.md` is the trace; every number this README or the dbt
   model comments cite (Gombe completeness figures, MSDAT's own denominator
   text, MSDAT's own reporting-lag disclaimer, GRID3's dataset and license)
   is quoted or linked there. The three specific rejected claims named in the
   acceptance criteria ("38% stock-out" as a national figure, "78,000
   zero-dose children" generalized beyond its actual scope, an unverified
   "two-month MSDAT latency") do not appear anywhere in this repo.
4. **States its Accountable Autonomy level with justification tied to
   severity/reversibility.** See [Accountable Autonomy level](#accountable-autonomy-level)
   above.
5. **Explicit honesty section: real / synthetic / mocked / not-attempted.**
   See [Honesty section](#honesty-section) above.

## Scope boundaries

Explicitly out of scope for this build (see `.claude/loopr/baby_prd.md` for
the full locked spec this was built against): national-scale rollout;
geospatial clinic-siting / Open Buildings settlement discovery; any
generative LLM/RAG component; a cold-chain consequence simulator on
synthetic stock data; ingestion of any credential-gated source; Neo4j (no
genuine topology dependency exists in a data-quality-triangulation
architecture); any hosted or continuously-scheduled deployment; any attempt
to fix, replace, or acquire credentialed access to DHIS2/MSDAT itself.

## Repository layout

```

                     models (ConfigDict(extra="forbid") everywhere), mypy
                     --strict clean.
  config.py          Every ID, indicator, and formula this pipeline relies
                      on, with a citation of where it came from.
  models.py           Pydantic record types.
  msdat_key_discovery.py  Extracts MSDAT's public frontend-auth key pair from its
                           own live JS at run time -- never hardcoded, see
```
